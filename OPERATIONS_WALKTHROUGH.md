# OPERATIONS_WALKTHROUGH — пооперационный разбор «Игровой базы данных»

> Этот документ объясняет проект **от операций**, а не от файлов. Идея простая:
> на защите тебя спросят не «что лежит в `db.py`», а «что происходит, когда
> пользователь нажимает кнопку». Поэтому здесь каждая операция разобрана по
> шагам — какой маршрут срабатывает, какую функцию `db.py` он зовёт, какой SQL
> уходит в PostgreSQL (на словах) и какой шаблон рисуется в ответ.
>
> Всё строго по реальному коду (`app.py`, `db.py`, `validators.py`, шаблоны).
> Сниппеты короткие — это ссылки-ориентиры на настоящие строки, а не копии
> файлов. Читай раздел A как «мысленную модель», а раздел B — как сценарии,
> которые почти можно зачитать вслух.

---

## РАЗДЕЛ A. Как Flask обрабатывает один запрос (общая механика)

Прежде чем разбирать операции, держи в голове одну картинку. Любая операция —
это один и тот же цикл, меняются только детали.

**1. Браузер шлёт запрос.**
Пользователь кликает ссылку или нажимает кнопку формы. Браузер отправляет
HTTP-запрос: метод (`GET` — «покажи мне страницу», `POST` — «прими мои данные»),
адрес (`/game/3`, `/login`, …) и, если это форма, тело с полями.

**2. Flask находит нужную функцию по адресу (маршрутизация).**
В `app.py` над каждой функцией стоит декоратор `@app.route(...)`. Flask смотрит
на адрес и метод запроса и вызывает ту функцию, чей `@app.route` совпал.
Например `GET /game/3` → функция `game_detail(game_id=3)`.

**3. Перед самой функцией всегда срабатывают «прослойки».**
Это код, который Flask выполняет на *каждый* запрос, ещё до маршрута:

- `@app.before_request → check_csrf()` (`app.py:42`) — если метод мутирующий
  (`POST/PUT/PATCH/DELETE`), проверяет CSRF-токен. У `GET` проверки нет.
- `@app.context_processor → inject_user()` (`app.py:58`) — кладёт `current_user`
  в каждый будущий шаблон.
- `@app.context_processor → inject_csrf()` (`app.py:67`) — кладёт `csrf_token`
  в каждый будущий шаблон.

Про context_processor подробно — в разделе C; про CSRF — в разделе D.

**4. Функция-обработчик выполняет логику.**
Внутри маршрута происходит «работа»: прочитать параметры (`request.args` для
GET, `request.form` для POST), проверить вход через `validators.py`, и — главное —
вызвать одну или несколько функций из `db.py`. Сам маршрут **SQL не пишет**, он
только зовёт именованные функции.

**5. `db.py` ходит в PostgreSQL.**
Каждая функция `db.py` открывает соединение (`get_connection()`), выполняет
**параметризованный** SQL и возвращает результат как обычные Python-словари
(`row_factory=dict_row`). Соединение закрывается автоматически через `with`.

**6. Функция возвращает ответ — одно из двух.**
- `render_template("шаблон.html", ...)` — Jinja2 берёт шаблон, подставляет
  данные и собирает готовый HTML.
- `redirect(url_for("другой_маршрут"))` — говорит браузеру «иди по другому
  адресу» (типичный финал любого POST: сохранили → отправили на страницу-итог).

**7. Ответ уходит в браузер.**
Браузер либо рисует полученный HTML, либо (при редиректе) делает новый запрос
по указанному адресу — и цикл повторяется.

> **Запомни одну фразу для защиты:**
> «Запрос → Flask по адресу выбирает функцию → функция валидирует ввод и зовёт
> `db.py` → `db.py` выполняет параметризованный SQL → функция возвращает либо
> отрисованный шаблон, либо редирект → ответ уходит в браузер».

Всё, что ниже, — это вариации этого одного цикла.

## РАЗДЕЛ B. Пооперационный разбор

Каждая операция оформлена так, чтобы её можно было зачитать вслух: «Когда
пользователь делает X — сначала…, затем…, в итоге он видит…».

### Операция 1. Открытие главной (каталог + блок рекомендаций)

**Маршрут:** `@app.route("/") def index()` — `app.py:96`.

Когда пользователь открывает `/`:

1. **Flask вызывает `index()`.** Метод `GET`, поэтому CSRF-проверка пропускается.
2. **Читаются фильтры из строки запроса.** `genre_id` и `tag_id` берутся из
   `request.args` и тут же прогоняются через `safe_int()` (`app.py:98-99`).
   На чистой главной их нет → оба становятся `None`.
3. **Выбирается список игр.** Раз фильтров нет, зовётся `db.get_all_games()`
   (`app.py:104`). Эта функция выполняет `SELECT` всех игр с `LEFT JOIN`
   на разработчика и издателя, `ORDER BY title` (`db.py:24`).
4. **Подгружаются справочники для выпадающих списков фильтров** —
   `db.get_all_genres()` и `db.get_all_tags()` (`app.py:106-107`): простые
   `SELECT id, name … ORDER BY name`.
5. **Считаются рекомендации** (`app.py:110-115`). Если пользователь залогинен
   (`session["user_id"]` есть) — зовётся `db.get_recommendations(user_id, 4)`.
   Если гость — `db.get_global_top(4)`, и каждой строке проставляется
   `source="global"`.
6. **Рендерится `index.html`** со всеми данными (`app.py:117`).
7. **Шаблон рисует страницу.** Сверху — блок «🎮 Рекомендуем вам», если список
   не пуст (`index.html:9`); подпись «На основе ваших оценок» или «Популярное
   сейчас» зависит от `source` первой карточки (`index.html:14`). Ниже — форма
   поиска, форма фильтров и сетка карточек игр.

**Что видит пользователь:** заголовок «Каталог игр», блок рекомендаций (для
гостя — популярное), поиск, фильтры и карточки всех игр.

*(Как именно работают рекомендации — см. операцию 1 в деталях ниже разбора 7,
а формально SQL расписан в `CODE_OVERVIEW.md`, раздел 2.2. Здесь главное —
маршрут принимает решение «личные или глобальные».)*

### Операция 2. Поиск игры

**Маршрут:** `@app.route("/search") def search()` — `app.py:149`.

Когда пользователь вводит текст в строку поиска на главной и жмёт «🔍 Найти»:

1. **Браузер шлёт `GET /search?q=ведьмак`.** Форма поиска — это GET-форма
   (`index.html:40`), поэтому запрос уходит в адресной строке, без тела и без
   CSRF (у GET его нет).
2. **Flask вызывает `search()`.** Функция читает `q` из `request.args`
   и обрезает пробелы (`app.py:151`).
3. **Если строка пустая** — ничего не ищем, `games = []`.
4. **Если строка есть — сначала валидация.** `validate_search_query(query)`
   (`app.py:154`) проверяет только длину (≤ 200 символов, `validators.py:75`).
   Если ошибки нет — зовётся `db.search_games(query)` (`app.py:156`).
5. **`db.search_games` идёт в БД** (`db.py:128`). SQL: `… WHERE g.title ILIKE %s`,
   где параметром передаётся `"%query%"` (`db.py:146`). `ILIKE` — поиск без учёта
   регистра; `%` по краям — «содержит подстроку». Строка пользователя **не
   склеивается** в SQL, она идёт отдельным параметром — это защита от инъекций.
6. **Рендерится `search.html`** со списком найденного и исходным запросом
   (`app.py:157`).

**Что видит пользователь:** страницу «🔍 Поиск игр», число результатов и сетку
найденных карточек — либо сообщение «ничего не найдено».

### Операция 3. Фильтрация каталога по жанру/тегу

**Маршрут:** тот же `index()` — `app.py:96`. Разница в том, что в адресе теперь
есть параметры.

Когда пользователь выбирает в выпадающих списках жанр и/или тег и жмёт «Показать»:

1. **Браузер шлёт `GET /?genre_id=2&tag_id=5`.** Форма фильтров — тоже GET
   (`index.html:46`), значения берутся из выбранных `<option>`.
2. **`index()` читает и обеззараживает оба id.** `safe_int()` (`validators.py:84`)
   приводит каждое к `int ≥ 1` или к `None`. Любой мусор («abc», «-1», «0»)
   превращается в `None` — никакой склейки строк с пользовательским вводом.
3. **Так как хотя бы один фильтр задан** (`app.py:101`), зовётся
   `db.get_games_filtered(genre_id, tag_id)` (`app.py:102`).
4. **`get_games_filtered` выполняет хитрый SQL** (`db.py:317`). Ключевых приёма
   два:
   - Условие на id стоит в `ON` у `LEFT JOIN`, а не в `WHERE`:
     `LEFT JOIN game_genres gg ON g.game_id = gg.game_id AND gg.genre_id = %s`.
     Затем `WHERE (%s::int IS NULL OR gg.genre_id IS NOT NULL)` — если фильтр
     не задан, условие пропускает строку; если задан — оставляет только игры,
     где связь нашлась. То же для тегов. Два условия соединены через `AND`.
   - `%s::int IS NULL` — **явный каст** к `int`. Без него PostgreSQL не мог
     вывести тип у параметра-`NULL` и падал с ошибкой `IndeterminateDatatype`
     (это уже чинили, см. `PROJECT_LOG.md`).
5. **Рендерится тот же `index.html`** — но в нём `selected_genre`/`selected_tag`
   подсветят выбранные пункты, а над сеткой появится «Найдено: N игр»
   (`index.html:76`).

**Что видит пользователь:** отфильтрованный каталог; если совпадений нет —
«По выбранным фильтрам ничего не найдено» с ссылкой «Сбросить».

### Операция 4. Открытие страницы игры

**Маршрут:** `@app.route("/game/<int:game_id>") def game_detail(game_id)` —
`app.py:128`. Часть `<int:game_id>` означает: Flask сам возьмёт число из адреса
и передаст его в функцию.

Когда пользователь кликает на название игры в каталоге:

1. **Браузер шлёт `GET /game/3`.**
2. **Flask вызывает `game_detail(game_id=3)`.**
3. **Загружается карточка** — `db.get_game_by_id(3)` (`app.py:130`). Эта функция
   делает в одном соединении 4–5 запросов (`db.py:45`):
   - главный `SELECT` с `LEFT JOIN` на разработчика, издателя и `ratings`,
     где `ROUND(AVG(r.score),1)` даёт среднюю оценку, а `COUNT(r.score)` —
     число оценок (`db.py:50`);
   - отдельные простые `SELECT` для жанров, тегов и платформ (через
     связующие таблицы);
   - `SELECT` ссылок на магазины, обёрнутый в `try/except` — если таблицы нет,
     вернётся пустой список (`db.py:115`).
4. **Если игра не найдена** (`game is None`) — `abort(404)` (`app.py:131`).
5. **Если пользователь залогинен** — подгружается его собственная оценка этой
   игры, `db.get_user_rating(user_id, game_id)` (`app.py:137`), чтобы подсветить
   уже нажатую цифру.
6. **Подбираются похожие игры** — `db.get_similar_games(game_id, 4)`
   (`app.py:139`). SQL берёт игры, у которых есть теги исходной игры
   (`tag_id IN (SELECT … WHERE game_id=%s)`), исключает саму игру и считает
   `COUNT(*) AS shared_tags`, сортируя по числу общих тегов (`db.py:351`).
7. **Рендерится `game.html`** (`app.py:141`). Шаблон рисует заголовок (с кнопкой
   «✏️ Редактировать» только если `current_user.is_admin`, `game.html:13`),
   бейдж средней оценки, мета-строку, платформы/жанры/теги, описание, форму
   оценки 1–10 (только для залогиненных, `game.html:89`), кнопки магазинов и
   блок похожих игр.

**Что видит пользователь:** полную карточку игры со всей мета-информацией,
возможностью оценить и блоком «Похожие игры».

### Операция 5. Регистрация

**Маршрут:** `@app.route("/register", methods=["GET","POST"]) def register()` —
`app.py:197`.

Когда пользователь открывает «Регистрация», заполняет форму и отправляет её:

1. **GET-часть.** Браузер шлёт `GET /register`. Если пользователь уже залогинен,
   его сразу редиректит на `/` (`app.py:199`). Иначе рисуется `register.html` —
   форма с полями `username/email/password` и скрытым `csrf_token`.
2. **POST-часть.** Пользователь жмёт «Зарегистрироваться» → `POST /register`
   с телом формы.
3. **Сначала срабатывает CSRF-проверка** в `before_request` (см. раздел D);
   без валидного токена — `abort(400)`.
4. **Маршрут читает поля** из `request.form` (`app.py:204-206`).
5. **Валидация по очереди** (`app.py:208-210`): `validate_username` (длина +
   разрешённые символы), `validate_email` (формат), `validate_password`
   (длина ≥ 8). Оператор `or` останавливается на первой ошибке.
6. **Если ошибок нет** — пароль хэшируется `generate_password_hash(password)`
   (`app.py:214`) и зовётся `db.create_user(username, email, password_hash)`
   (`app.py:215`). SQL: `INSERT INTO users (...) VALUES (%s,%s,%s) RETURNING
   user_id` (`db.py:158`). **В БД попадает только хэш**, не сам пароль.
7. **Новый `user_id` кладётся в сессию** (`app.py:216`) — пользователь сразу
   залогинен — и идёт `redirect` на `/` с флэш-приветствием.
8. **Если имя или email заняты** — `db.create_user` бросает `UniqueViolation`,
   маршрут ловит её и показывает «Такое имя пользователя или email уже занято»
   (`app.py:219`), снова рендеря форму.

**Что видит пользователь:** при успехе — главную с приветствием «Добро
пожаловать!»; при ошибке — ту же форму с понятным сообщением.

### Операция 6. Вход и выход

**Маршруты:** `login()` — `app.py:229`; `logout()` — `app.py:253`.

**Вход.** Когда пользователь заполняет форму входа и отправляет её:

1. **GET `/login`** рисует `login.html` (если уже залогинен — сразу на `/`,
   `app.py:231`).
2. **POST `/login`** — после CSRF-проверки маршрут читает `username` и `password`
   (`app.py:236-237`).
3. **Ищется пользователь** — `db.get_user_by_username(username)` (`app.py:239`).
   SQL возвращает строку, включая `password_hash` и `is_admin` (`db.py:169`).
4. **Проверка пароля** — `check_password_hash(user["password_hash"], password)`
   (`app.py:241`). Сравнивается хэш, не открытый пароль.
5. **Если пользователь не найден ИЛИ пароль не сошёлся** — одно обобщённое
   сообщение «Неверный логин или пароль» (`app.py:242`). Намеренно не уточняем,
   что именно неверно — чтобы не подсказывать перебору, существует ли логин.
6. **Если всё верно** — `session["user_id"] = user["user_id"]` (`app.py:244`)
   и `redirect` на `/` с приветствием.

**Выход.** `@app.route("/logout", methods=["POST"])` (`app.py:253`):

1. Кнопка «Выход» в шапке — это **мини-форма POST** со скрытым `csrf_token`
   (`base.html:21`), а не просто ссылка. Это нужно, чтобы выход тоже был защищён
   CSRF.
2. POST проходит CSRF-проверку, затем `session.clear()` стирает сессию
   (`app.py:255`) и редиректит на `/` с сообщением «Вы вышли из аккаунта».

**Что видит пользователь:** при входе — главную «С возвращением!»; при выходе —
главную как гость.

### Операция 7. Оценка игры

**Маршрут:** `@app.route("/rate/<int:game_id>", methods=["POST"]) def
rate_game(game_id)` — `app.py:162`.

Когда пользователь на карточке игры нажимает цифру от 1 до 10:

1. **Браузер шлёт `POST /rate/3`.** Каждая из 10 кнопок — это `submit` с
   `name="score"` и своим `value` (`game.html:95`), в форме есть скрытый
   `csrf_token` (`game.html:92`).
2. **CSRF-проверка** в `before_request` (метод POST).
3. **Проверка входа.** Если `session["user_id"]` нет — flash «Войдите, чтобы
   оставить оценку» и redirect на `/login` (`app.py:165-167`).
4. **Валидация оценки.** `validate_score(score_raw)` (`app.py:170`) проверяет,
   что это целое от 1 до 10 (`validators.py:62`). Если ошибка — flash с текстом.
5. **Если всё ок** — `db.set_rating(user_id, game_id, int(score_raw))`
   (`app.py:174`). SQL — **upsert**: `INSERT INTO ratings (...) VALUES (...)
   ON CONFLICT (user_id, game_id) DO UPDATE SET score = EXCLUDED.score,
   created_at = now()` (`db.py:203`). То есть «поставить оценку, а если она уже
   была — обновить». Составной PRIMARY KEY гарантирует одну оценку на пару
   пользователь–игра. На стороне БД есть ещё `CHECK (score BETWEEN 1 AND 10)`.
6. **Редирект обратно на карточку** `/game/3` (`app.py:177`) — там уже видно
   новую среднюю оценку и подсвеченную цифру.

**Что видит пользователь:** ту же карточку игры с флэш-сообщением «Оценка N
сохранена ⭐» и обновлённой подсветкой выбранной цифры.

### Операция 8. Открытие профиля

**Маршрут:** `@app.route("/profile") def profile()` — `app.py:182`.

Когда пользователь нажимает на своё имя в шапке:

1. **Браузер шлёт `GET /profile`.**
2. **Проверка входа.** Если не залогинен — flash «Войдите, чтобы просмотреть
   профиль» и redirect на `/login` (`app.py:185-187`).
3. **Загружаются оценки** — `db.get_user_ratings(user_id)` (`app.py:189`). SQL
   соединяет `ratings` и `games`, фильтрует по `user_id`, сортирует
   `ORDER BY score DESC, title` (`db.py:230`).
4. **Загружается статистика** — `db.get_user_stats(user_id)` (`app.py:190`). SQL:
   `COUNT(*) AS games_rated, ROUND(AVG(score),1) AS avg_score_given` (`db.py:251`).
   Если оценок нет — `games_rated = 0`, средняя — `NULL`.
5. **Рендерится `profile.html`** (`app.py:192`). Само имя, аватар и дата
   регистрации берутся из `current_user` (его кладёт `inject_user`, см. раздел C),
   а статистика и список — из переданных `stats`/`ratings`.

**Что видит пользователь:** шапку профиля (аватар, имя, дата регистрации),
плитку статистики и список оценённых им игр.

### Операция 9. Добавление игры (админ)

**Маршрут:** `@app.route("/admin/add_game", methods=["GET","POST"])
@admin_required def admin_add_game()` — `app.py:262`.

> Сначала **всегда** работает декоратор `@admin_required` (`app.py:75`): гость →

## РАЗДЕЛ D. CSRF-токен простыми словами

### Что это за атака

CSRF (Cross-Site Request Forgery, «подделка межсайтового запроса») работает так.
Ты залогинен на нашем сайте — у тебя в браузере лежит сессионная кука. Ты
заходишь на чужой вредоносный сайт, а там спрятана форма, которая втихую
отправляет POST на наш адрес, например `/rate/3` или даже `/logout`. Браузер
**автоматически прикладывает твою куку** к этому запросу — и сервер думает, что
действие совершил ты. Так злоумышленник может выполнять действия от твоего имени,
не зная ни логина, ни пароля.

### Как токен закрывает эту атаку

Идея: на каждое мутирующее действие требовать секрет, которого у чужого сайта
быть не может. Мы генерируем случайный **CSRF-токен**, кладём его в сессию
(на сервере) и одновременно — в скрытое поле каждой нашей формы. Когда приходит
POST, сервер сверяет токен из формы с токеном из сессии:

- наша форма знает токен (мы сами его туда вставили) → проверка проходит;
- чужая форма токен **не знает** (она не видит содержимое нашей сессии и не
  может прочитать наш HTML из-за политики браузера) → проверка падает,
  `abort(400)`.

Кука сама по себе уже не «пропуск»: нужен ещё токен, который есть только у наших
страниц.

### Где это в коде

1. **Генерация — `get_csrf_token()`** (`app.py:35-39`):
   ```python
   if "csrf_token" not in session:
       session["csrf_token"] = secrets.token_hex(32)
   return session["csrf_token"]
   ```
   Случайные 32 байта в шестнадцатеричном виде, сохраняются в сессии при первом
   обращении.

2. **Прокидывание во все шаблоны — `inject_csrf`** (`app.py:67-70`):
   context_processor кладёт `csrf_token` в каждый шаблон, поэтому любая форма
   может вставить его без ручной передачи.

3. **Проверка на каждый мутирующий запрос — `check_csrf` в `before_request`**
   (`app.py:42-53`):
   ```python
   if request.method in ("POST", "PUT", "PATCH", "DELETE"):
       session_token = session.get("csrf_token", "")
       form_token    = request.form.get("csrf_token", "")
       if not session_token or not hmac.compare_digest(session_token, form_token):
           abort(400)
   ```
   `hmac.compare_digest` сравнивает строки за **постоянное время** — не «выходит
   раньше» на первом несовпавшем символе, что защищает от timing-атак (подбора
   токена по времени ответа). Пустой токен в сессии — всегда отказ.

4. **Скрытые поля `csrf_token` в формах.** Каждая POST-форма содержит
   `<input type="hidden" name="csrf_token" value="{{ csrf_token }}">`:
   - выход — `base.html:22`;
   - оценка игры — `game.html:92`;
   - регистрация — `register.html` (поле формы);
   - вход — `login.html` (поле формы);
   - добавление и редактирование игры — `admin_add_game.html` /
     `admin_edit_game.html`.

   А вот **GET-формы** (поиск `index.html:40`, фильтры `index.html:46`) токена
   **не** содержат и не проверяются — GET ничего не меняет в БД, и CSRF им не
   грозит.

> **Фраза для защиты:** «CSRF — это когда чужой сайт от моего имени шлёт запрос,
> пользуясь моей кукой. Я завёл случайный токен: он лежит в сессии и в скрытом
> поле каждой формы. На каждый POST `before_request` сверяет их через
> `hmac.compare_digest`; у чужой формы токена нет — значит, `abort(400)`».

## РАЗДЕЛ E. Полный разбор `db.py` сверху вниз

> В этом разделе **каждая SQL-конструкция и каждый метод поясняются прямо
> в скобках** при первом появлении и повторяются дальше — чтобы не приходилось
> держать всё в голове. Если уже знаешь конструкцию — просто пропускай скобки.

### Мини-словарь (то, что встречается чаще всего)

Чтобы дальше не повторять одно и то же длинно, вот короткий справочник —
к нему можно возвращаться:

- **`SELECT`** — «выбери/прочитай данные». Читающая команда, ничего не меняет.
- **`INSERT`** — «вставь новую строку».
- **`UPDATE`** — «измени существующие строки».
- **`DELETE`** — «удали строки».
- **`WHERE`** — «условие отбора»: какие строки брать (`WHERE user_id = 5`).
- **`JOIN` / `INNER JOIN`** — «склей две таблицы по совпадению»; строка попадёт
  в результат, только если совпадение нашлось в обеих.
- **`LEFT JOIN`** — то же, но левая (главная) таблица остаётся, даже если справа
  совпадения нет (недостающее заполнится `NULL`).
- **`USING (col)`** — короткая запись условия склейки, когда колонка в обеих
  таблицах называется одинаково (вместо `ON a.col = b.col`).
- **`ON`** — «условие склейки» для `JOIN` (когда `USING` не подходит).
- **`GROUP BY`** — «сгруппируй строки» — нужно, когда считаешь агрегаты по группам.
- **Агрегаты** — функции над группой строк: **`COUNT(*)`** (сколько строк),
  **`AVG(x)`** (среднее), **`SUM(x)`** (сумма).
- **`ROUND(x, 1)`** — округлить число до 1 знака после запятой.
- **`ORDER BY … DESC/ASC`** — «отсортируй результат» (DESC — по убыванию).
- **`LIMIT n`** — «верни не больше n строк».
- **`DISTINCT`** — «убери одинаковые строки из результата».
- **`%s`** — плейсхолдер параметра: настоящее значение psycopg подставит
  отдельно и безопасно (защита от SQL-инъекций).
- **`RETURNING col`** — «после вставки/обновления верни мне это поле» (например,
  id только что созданной строки).
- **методы курсора:** **`cur.execute(sql, values)`** — выполнить запрос;
  **`cur.fetchone()`** — взять одну строку (или `None`); **`cur.fetchall()`** —
  взять все строки списком.

---

`db.py` — это **единственное место, где живёт SQL**. Маршруты в `app.py` про
HTTP, валидаторы про проверку ввода, а `db.py` — про данные. Все 24 функции
построены по одному шаблону:

```python
def какая_то_функция(параметры):
    sql = "… %s …"                       # запрос с плейсхолдером %s
    with get_connection() as conn:        # открыть соединение к БД
        with conn.cursor() as cur:        # открыть курсор (через него шлём запросы)
            cur.execute(sql, (значения,)) # execute — выполнить запрос с параметрами
            return cur.fetchall()         # fetchall — забрать все строки результата
```

**Зачем именно так:**
- `with get_connection()` и `with conn.cursor()` (`with` — менеджер контекста) —
  соединение и курсор **закрываются сами**, даже если внутри случилась ошибка
  (не нужно вручную звать `.close()`).
- `cur.execute(sql, (values,))` (`execute` — «выполни этот SQL») — значения
  передаются **отдельным аргументом**, а не вклеиваются в строку SQL. Это и есть
  параметризация — защита от SQL-инъекций. Нигде в файле нет `f"… {переменная} …"`
  внутри SQL.
- `cur.fetchall()` (вернуть все строки) / `cur.fetchone()` (вернуть одну) — так
  мы достаём результат `SELECT` в Python.
- Благодаря `row_factory=dict_row` (см. ниже) каждая строка приходит как `dict`
  (словарь), поэтому в шаблонах можно писать `game.title`, а не `game[1]`.

### Подключение: `get_connection()` (`db.py:9-17`)

```python
def get_connection():
    return psycopg.connect(
        host=..., port=..., dbname=..., user=..., password=...,  # всё из .env
        row_factory=dict_row,
    )
```

**Зачем:** одна точка входа к БД. `psycopg.connect(...)` (метод драйвera —
«установи соединение с PostgreSQL») получает параметры из `.env` через
`os.getenv` (`db.py:1-6`), поэтому пароль не лежит в коде. По факту в `.env`
прописана учётка `gamedb_app` — роль с минимальными правами (только
`SELECT/INSERT/UPDATE/DELETE` — читать и менять данные; без DDL — то есть без
права `CREATE`/`DROP`/`ALTER`, меняющего саму структуру таблиц).
`row_factory=dict_row` (настройка «как отдавать строки») — чтобы строки были
словарями, а не кортежами. Все остальные функции зовут именно `get_connection()`,
а не подключаются сами — если завтра поменяются параметры, править нужно одно
место.

### Группа 1. Каталог

**`get_all_games()`** (`db.py:24`) — все игры для главной.
`SELECT` (прочитать) игр с `LEFT JOIN developers` (приклеить имя разработчика,
оставив игру даже без него) и `LEFT JOIN publishers` (то же для издателя),
`ORDER BY title` (отсортировать по названию).
**Зачем `LEFT JOIN` (а не `INNER JOIN`):** игра покажется, даже если у неё не
указан разработчик или издатель; `INNER JOIN` (склейка только при совпадении)
такую игру бы выкинул. **Зачем `USING (developer_id)`:** короткая запись условия
склейки, когда колонка называется одинаково в обеих таблицах.

**`get_game_by_id(game_id)`** (`db.py:45`) — полная карточка для `/game/<id>`.
Делает **4–5 запросов в одном курсоре**:
1. главный `SELECT` (прочитать) с `LEFT JOIN ratings` (приклеить оценки) +
   `GROUP BY` (сгруппировать строки оценок по игре, чтобы посчитать агрегаты),
   где `ROUND(AVG(r.score), 1)` (`AVG` — среднее всех оценок, `ROUND(…,1)` —
   округлить до 1 знака) — средняя оценка, а `COUNT(r.score)` (`COUNT` — сколько
   оценок) — их число;
2. жанры (`game_genres + genres`), 3. теги, 4. платформы — простыми отдельными
   `SELECT`;
5. ссылки на магазины — в `try/except` (`db.py:115`; перехват ошибки), чтобы при
   отсутствии таблицы вернуть пустой список, а не упасть.
Если главный запрос ничего не вернул (`cur.fetchone()` дал `None`) — функция
отдаёт `None`, и маршрут делает `abort(404)`. **Зачем дробить на несколько
запросов:** так проще и читаемее, чем один монстр-запрос с агрегатами по
жанрам/тегам/платформам сразу.

### Группа 2. Поиск

**`search_games(query)`** (`db.py:128`) — поиск по названию.
`… WHERE g.title ILIKE %s` (`WHERE` — условие отбора; `ILIKE` — сравнение строк
без учёта регистра; `%s` — плейсхолдер), параметр — `"%query%"` (`db.py:146`).
**Зачем `ILIKE`:** регистронезависимый поиск («ВЕДЬМАК» найдёт «Ведьмак»).
**Зачем `%…%` (символ `%` внутри строки шаблона):** означает «любой текст до и
после» → «название содержит подстроку». Главное — строка пользователя идёт
**параметром** через `%s`, а не вклеивается; psycopg её экранирует.

### Группа 3. Пользователи

**`create_user(username, email, password_hash)`** (`db.py:154`) — регистрация.
`INSERT INTO users (...) VALUES (%s,%s,%s) RETURNING user_id` (`INSERT` — вставить
новую строку; `VALUES` — её значения; `RETURNING user_id` — сразу вернуть id
созданной строки).
**Зачем `RETURNING`:** получить id новой строки, чтобы положить его в сессию, без
отдельного `SELECT` следом. При дубле username/email БД сама бросит
`UniqueViolation` (нарушение ограничения `UNIQUE` — «значение должно быть
уникальным»), а маршрут её поймает.

**`get_user_by_username(username)`** (`db.py:169`) — для логина.
`SELECT … WHERE username = %s` — возвращает строку **с** `password_hash` и
`is_admin`. **Зачем хэш:** нужен, чтобы сверить пароль через
`check_password_hash`. Это единственная функция, отдающая хэш наружу.

**`get_user_by_id(user_id)`** (`db.py:184`) — для сессии и шаблонов.
То же, но **без** `password_hash`, зато с `created_at`. Достаёт строку через
`cur.fetchone()` (одна строка или `None`). **Зачем:** именно её зовут
`inject_user` (для `current_user` во всех шаблонах) и `admin_required` (для
проверки `is_admin`). Хэш тут не нужен и наружу не отдаётся — лишнего не светим.

### Группа 4. Оценки

**`set_rating(user_id, game_id, score)`** (`db.py:203`) — поставить/изменить оценку.
```sql
INSERT INTO ratings (user_id, game_id, score) VALUES (%s,%s,%s)
ON CONFLICT (user_id, game_id) DO UPDATE SET score = EXCLUDED.score, created_at = now()
```
- `INSERT … VALUES` — пытаемся вставить новую оценку.
- `ON CONFLICT (user_id, game_id)` — «если такая пара уже существует» (сработает
  ограничение уникальности по этим двум колонкам).
- `DO UPDATE SET …` — «тогда не падай, а обнови существующую строку».
- `EXCLUDED.score` — это то значение `score`, которое мы пытались вставить
  (специальное слово для «новых» данных в `ON CONFLICT`).
- `now()` — функция БД, текущее время.

**Зачем `ON CONFLICT DO UPDATE` (это называют upsert — «update + insert»):** один
запрос делает «вставь, а если у этого пользователя для этой игры оценка уже есть —
обнови». Не нужно сначала `SELECT`-ить, есть ли запись. Составной PRIMARY KEY
(первичный ключ из двух колонок) `(user_id, game_id)` гарантирует одну оценку на
пару.

**`get_user_rating(user_id, game_id)`** (`db.py:216`) — оценка пользователя для
одной игры. `SELECT score FROM ratings WHERE …`, возвращает `int` или `None`.
**Зачем:** чтобы на карточке подсветить уже нажатую цифру (`game.html`).

### Группа 5. Профиль

**`get_user_ratings(user_id)`** (`db.py:230`) — все оценённые игры.
`JOIN ratings + games` (склеить оценки с играми, чтобы знать названия) `WHERE
user_id = %s` (только этого пользователя) `ORDER BY score DESC, title` (сортировка:
сначала по оценке по убыванию, при равенстве — по названию).
**Зачем сортировка:** в профиле сверху показываем то, что пользователь оценил выше.

**`get_user_stats(user_id)`** (`db.py:251`) — статистика.
`COUNT(*) AS games_rated` (`COUNT(*)` — сколько всего строк-оценок; `AS games_rated`
— дать колонке имя в результате), `ROUND(AVG(score), 1) AS avg_score_given`
(средняя оценка, округлённая).
**Зачем:** плитка «сколько оценил / средняя оценка». Если оценок нет — `count = 0`,
средняя `NULL` (пустое значение).

### Группа 6. Справочники и фильтрация

**`get_all_genres()` / `get_all_tags()` / `get_all_developers()` /
`get_all_publishers()` / `get_all_platforms()`** (`db.py:272-314`) — одинаковые
простые `SELECT id, name … ORDER BY name` (прочитать id и имя, отсортировать по
имени). **Зачем:** наполнить выпадающие списки и чекбоксы — в фильтрах каталога и
в админских формах.

**`get_games_filtered(genre_id, tag_id)`** (`db.py:317`) — каталог с фильтром.
Два хитрых приёма:
- условие на id стоит в `ON` (условие склейки) у `LEFT JOIN`
  (`… AND gg.genre_id = %s`), а в `WHERE` (условие отбора) — проверка
  `(%s::int IS NULL OR gg.genre_id IS NOT NULL)`. `IS NULL` — «значение пустое»,
  `IS NOT NULL` — «значение есть». Если фильтр не задан (параметр `NULL`) —
  условие пропускает строку; если задан — оставляет только игры, где склейка
  нашлась. Так один запрос работает для всех комбинаций «жанр / тег / оба / ничего».
- `%s::int IS NULL` — `::int` это **явный каст** (приведение типа: «считай этот
  параметр целым числом»). Без него PostgreSQL не понимал тип у параметра-`NULL`
  и падал с ошибкой `IndeterminateDatatype` («не могу определить тип»; этот баг
  уже чинили).

**Зачем `SELECT DISTINCT` (убрать дубликаты строк):** у игры может быть несколько
строк в `game_genres`/`game_tags`, из-за `JOIN` строки-игры могли бы задвоиться —
`DISTINCT` их сворачивает в одну.

### Группа 7. Рекомендации

**`get_similar_games(game_id, limit)`** (`db.py:351`) — похожие по тегам.
Берёт игры, у которых есть теги исходной игры —
`tag_id IN (SELECT … WHERE game_id=%s)` (`IN (…)` — «значение входит в этот
список/результат подзапроса»), исключает саму игру `g.game_id != %s` (`!=` — «не
равно»), считает `COUNT(*) AS shared_tags` (сколько общих тегов) и сортирует по
нему `ORDER BY shared_tags DESC` (по убыванию), `LIMIT %s` (не больше N строк).
**Зачем:** блок «Похожие игры» на карточке.

**`get_global_top(limit, exclude_user_id)`** (`db.py:379`) — глобальный топ по
средней оценке. `JOIN ratings` (склеить с оценками), `ROUND(AVG(r.score), 1)`
(средняя оценка), `ORDER BY avg_score DESC, ratings_count DESC` (сначала по
средней, при равенстве — у кого больше оценок). Если задан `exclude_user_id` —
через `NOT EXISTS (SELECT 1 …)` (`NOT EXISTS` — «строк по этому условию не
существует»; `SELECT 1` — нам не важны сами данные, важен лишь факт наличия)
выкидывает игры, которые этот пользователь уже оценил. **Зачем именованные
параметры `%(uid)s`/`%(limit)s` (плейсхолдеры с именем, а не просто `%s`):** один
параметр (`uid`) подставляется в запрос дважды — с именами это нагляднее.
**Зачем функция:** топ для гостей **и** запасной вариант (fallback) для
рекомендаций.

**`get_recommendations(user_id, limit)`** (`db.py:411`) — **самая интересная
функция**. Алгоритм:
1. Отдельным `SELECT COUNT(*)` (посчитать строки) узнаём число оценок пользователя.
2. Если оценок **< 3** → «холодный старт»: возвращаем `get_global_top`
   без уже оценённых игр, помечая строки `source='global'`.
3. Иначе — **запрос с тремя CTE** (CTE = Common Table Expression, временный
   именованный подзапрос, объявляется через `WITH имя AS (…)`; читается как
   «промежуточный шаг»):
   - `taste` — «вкус по тегам»: средняя оценка пользователя по каждому тегу
     минус 5.5 (`AVG(r.score) - 5.5`; получается affinity: плюс — тег нравится,
     минус — нет);
   - `candidates` — игры, которые он ещё **не** оценивал (через `NOT EXISTS` —
     «нет такой строки в его оценках»);
   - `scored` — для каждого кандидата `SUM(t.affinity)` (`SUM` — сумма) складывает
     affinity всех его тегов; больше «любимых» тегов → выше `rec_score`. Итог
     сортируется `ORDER BY rec_score DESC` (по убыванию) с `LIMIT`.
4. Если личных рекомендаций меньше `limit` — **дополняем** глобальным топом,
   исключая уже оценённые (на стороне БД) и уже показанные (в Python через `set`
   — множество, быстрая проверка «уже видели этот id?»).
5. Каждой строке проставляется `source = 'personal' | 'global'` — по нему шаблон
   меняет подпись блока.
**Зачем CTE, а не один большой SELECT:** запрос читается как пайплайн из трёх
шагов — «посчитай вкус → возьми кандидатов → оцени их», это легко объяснить вслух.

### Группа 8. Транзакционные операции (создание/редактирование игры)

Это **главный пример ACID-атомарности** в проекте (атомарность = «всё или
ничего»). Обе функции делают всю работу в **одной транзакции** через
`with get_connection() as conn:` — при выходе из блока без ошибки psycopg 3 сам
делает `COMMIT` (зафиксировать все изменения), а при любом исключении —
`ROLLBACK` (откатить, будто ничего не было).

**`_clean_names(names)`** (`db.py:669`) — вспомогательная (Python, без SQL):
убирает пробелы, пустые строки и дубликаты, сохраняя порядок. **Зачем:**
подчистить списки «новых» имён перед `INSERT`.

**`create_game(...)`** (`db.py:683`) — создать игру. Шаги внутри транзакции:
- a) если задан `new_developer_name`/`new_publisher_name` — `INSERT … RETURNING
  id` (вставить и вернуть id; новое имя имеет приоритет над выбранным id);
- c) `INSERT INTO games (...) RETURNING game_id` (вставить игру и вернуть её id);
- b) для каждого нового жанра/тега/платформы — **find-or-create** («найди или
  создай»):
  `INSERT … ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name RETURNING id`.
  **Зачем фиктивный `DO UPDATE`, а не `DO NOTHING`:** `DO NOTHING` («при конфликте
  ничего не делай») в случае конфликта **не вернёт строку**, а нам нужен
  `RETURNING id` и для «создал», и для «уже было». «Обновление имени на то же
  самое» (`SET name = EXCLUDED.name`) — трюк, чтобы `RETURNING` сработал всегда;
- d) `INSERT` связей в `game_genres`/`game_tags`/`game_platforms`, причём по
  `set(...)` (множество — убирает повторы) — **дедупликация**, чтобы не упасть на
  PRIMARY KEY, если один id попал и из чекбокса, и из «новых имён».
Возвращает `game_id`. **Зачем транзакция:** если упасть на полпути — `ROLLBACK`
откатит всё, в БД не останется «полу-игры» без связей; либо всё, либо ничего.

**`get_game_for_edit(game_id)`** (`db.py:499`) — загрузить игру в форму
редактирования. `SELECT` полей `games` + отдельные `SELECT` списков текущих
`genre_ids/tag_ids/platform_ids`. **Зачем списки id:** чтобы шаблон отметил
`checked` уже выбранные чекбоксы. Возвращает `None`, если игры нет.

**`update_game(...)`** (`db.py:538`) — обновить игру. То же, что `create_game`,
с двумя отличиями:
- вместо `INSERT INTO games` — `UPDATE games SET … WHERE game_id=%s` (`UPDATE …
  SET` — изменить поля; `WHERE` — строго у одной игры);
- связи согласуются методом **«удалить и вставить заново»**: сначала
  `DELETE FROM game_genres/game_tags/game_platforms WHERE game_id=%s` (`DELETE` —
  удалить старые связи этой игры), затем `INSERT` всех выбранных id заново.
  **Зачем так:** связи многие-ко-многим — это набор галочек; проще снести старый
  набор и записать новый, чем вычислять разницу. Код одинаково верен и для
  добавления, и для снятия галочки. Внутри транзакции это безопасно: при сбое
  `ROLLBACK` откатит и `DELETE`-ы — старые связи останутся на месте.
