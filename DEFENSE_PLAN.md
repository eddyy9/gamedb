## 🃏 Сильные карты (вытаскивай их при любой возможности)

Это то, что отличает проект от «просто CRUD». Упоминай их и на слайдах, и в
ответах на вопросы:

1. **Рекомендательный CTE** — профиль вкуса по тегам (`affinity = AVG(score) −
   5.5`), три CTE-шага: taste → candidates → scored. Это «вкусный» SQL.
2. **Транзакционные добавление/правка игры** — наглядный пример ACID-атомарности:
   `with conn:` коммитит при успехе, откатывает при сбое; «полу-игры» не бывает.
3. **Роль `gamedb_app` с минимальными правами** — least privilege: приложение
   ходит в БД под ролью без DDL-прав (нельзя `DROP`/`ALTER`).
4. **Живой трюк с админкой** — `UPDATE users SET is_admin = TRUE` → обновил
   страницу → появились админ-функции. Эффектно и просто.
5. **ER-диаграмма с M:N через смежные таблицы** — `game_genres`, `game_tags`,
   `game_platforms` разносят связи «многие-ко-многим».
6. **Нормализация 3NF** — справочники вынесены, дублирования данных нет.

### Слайд 7 — Рекомендации (изюминка)
**[НА СЛАЙДЕ]**
- Два механизма:
  - **Персональные** — профиль вкуса по тегам (CTE)
  - **Похожие игры** — по общим тегам (item-based)
- Формула: `affinity = AVG(score) − 5.5` по каждому тегу
- 3 шага CTE: taste → candidates → scored
- «Холодный старт»: < 3 оценок → глобальный топ

**[ГОВОРИШЬ]**
> «Главная фишка — рекомендации. Работают два механизма. Первый — персональный:
> запрос с тремя CTE. Сначала считаю "вкус" — по каждому тегу беру среднюю оценку
> пользователя и вычитаю 5.5, середину шкалы. Получается affinity: плюс — тег
> нравится, минус — нет. Потом беру игры, которые он ещё не оценивал, и складываю
> affinity их тегов. Чем больше любимых тегов — тем выше игра в списке. Если оценок
> меньше трёх, вкус считать не на чем — показываю глобальный топ. Второй механизм —
> "похожие игры" на карточке: ищу игры с наибольшим числом общих тегов.»

### Слайд 8 — Работа с БД: транзакции и целостность
**[НА СЛАЙДЕ]**
- **ACID-атомарность**: добавление игры = одна транзакция
- `with conn:` → успех = COMMIT, ошибка = ROLLBACK
- Целостность: PRIMARY KEY, FOREIGN KEY, CHECK, UNIQUE, NOT NULL
- Нормализация **3NF** — справочники вынесены

**[ГОВОРИШЬ]**
> «Добавление игры — это много шагов: вставить разработчика, саму игру, создать
> новые жанры и теги, связать всё. Я обернул это в одну транзакцию. Если упасть на
> середине — срабатывает ROLLBACK, и в базе не остаётся "полу-игры". Это и есть
> атомарность, буква A в ACID. Целостность гарантирует сама схема: внешние ключи,
> ограничение CHECK на оценку от 1 до 10, уникальность логина. И база приведена к
> третьей нормальной форме — справочники вынесены, дублей нет.»

> токен из сессии, проверяется сравнением постоянного времени. Четвёртое —
> приложение ходит в базу под ролью `gamedb_app` с минимальными правами: она умеет
> только читать и менять данные, но не может `DROP` или `ALTER`. Принцип
> наименьших привилегий.»

## 🐘 ЧАСТЬ 3. Момент с psql (по шагам)

Заранее открой терминал. **Сначала `chcp 65001`** — иначе кириллица в описаниях
поломается.

```powershell
chcp 65001
psql -U postgres -d gamedb
```

1. **Структура базы:**
   ```
   \dt              -- список всех 12 таблиц
   \d games         -- столбцы и внешние ключи таблицы games
   \d ratings       -- видно CHECK (score 1..10) и составной PRIMARY KEY
   ```
   > «Вот таблицы. У `games` — внешние ключи на разработчика и издателя. У `ratings`
   > — ограничение CHECK на оценку и составной первичный ключ.»

2. **SELECT с JOIN:**
   ```sql
   SELECT g.title, d.name AS developer
   FROM games g
   JOIN developers d ON g.developer_id = d.developer_id
   ORDER BY g.title;
   ```
   > «Соединяю игры с разработчиками — игра хранит только id, имя берём из
   > справочника.»

3. **Доказать, что пароль захэширован:**
   ```sql
   SELECT user_id, username, is_admin, password_hash FROM users;
   ```
   > «Вот мой пользователь. Вместо пароля — длинный хэш, и `is_admin = f`.»

4. **Демонстрация ограничения CHECK** (безопасно, в транзакции):
   ```sql
   BEGIN;
   INSERT INTO ratings (user_id, game_id, score) VALUES (1, 2, 11);
   -- ERROR: ... violates check constraint "ratings_score_check"
   ROLLBACK;
   ```
   > «Пробую поставить оценку 11 — база отказывает. Правило живёт в схеме, обойти
   > нельзя.» *(подставь свой реальный user_id вместо 1)*

5. **Удаление внутри BEGIN … ROLLBACK** (показать, не сломав данные):
   ```sql
   BEGIN;
   DELETE FROM games WHERE title = 'Portal 2';
   SELECT COUNT(*) FROM games;     -- 7
   ROLLBACK;
   SELECT COUNT(*) FROM games;     -- снова 8
   ```
   > «Удаляю игру внутри транзакции — счётчик стал 7. Делаю ROLLBACK — снова 8. Это
   > безопасная песочница: пока нет COMMIT, изменения видны только мне.»

6. **Трюк с выдачей админки:**
   ```sql
   UPDATE users SET is_admin = TRUE WHERE username = 'ilya';
   ```
   > «`is_admin` — это столбец в `users`, то есть админ **приложения**, а не роль
   > базы. Сейчас выдам себе права...»
   Переключись в браузер, **обнови страницу**.
   > «...обновляю страницу — появились "Добавить игру" и "Редактировать". Приложение
   > читает флаг на каждый запрос, перезапуск не нужен.»

## ❓ ЧАСТЬ 4. Вероятные вопросы комиссии (с короткими ответами)

**Что такое ACID?**
> Atomicity (всё или ничего), Consistency (база всегда в согласованном состоянии),
> Isolation (транзакции не мешают друг другу), Durability (после COMMIT данные не
> потеряются). У меня атомарность видна в `create_game`: вся вставка — одна
> транзакция.

**Что такое MVCC в PostgreSQL?**
> Multi-Version Concurrency Control. PostgreSQL хранит несколько версий строки,
> поэтому читающие не блокируют пишущих и наоборот. Каждая транзакция видит
> «снимок» данных на момент своего старта. Поэтому моё `BEGIN … ROLLBACK` с
> удалением не мешает другим — они видят старую версию, пока я не закоммитил.

**Какой уровень изоляции по умолчанию?**
> `READ COMMITTED` — транзакция видит только закоммиченные данные, каждый запрос
> видит свежий снимок. Этого достаточно для моего приложения. PostgreSQL также
> поддерживает `REPEATABLE READ` и `SERIALIZABLE`.

**Что такое нормальная форма? В какой ваша база?**
> Нормализация убирает дублирование. 1NF — атомарные значения; 2NF — нет
> зависимости от части ключа; 3NF — нет зависимости одних неключевых полей от
> других. Моя база в **3NF**: справочники (жанры, теги, разработчики) вынесены в
> отдельные таблицы, связи M:N — через смежные таблицы, дублей данных нет.

**Почему без ORM?**
> Это курс по базам данных — нужно показывать SQL, а не прятать его. На голом
> psycopg видно каждый JOIN, CTE, транзакцию. ORM был бы уместен в продакшене, но
> не для учебной демонстрации работы с БД.

**Как защищаетесь от SQL-инъекций?**
> Все запросы параметризованы: значения передаются через плейсхолдеры `%s`
> отдельным аргументом, psycopg их экранирует. Пользовательский ввод никогда не
> склеивается в строку SQL. Плюс id из URL прогоняются через `safe_int`.

**Как будете масштабировать?**
> Добавить **индексы** на часто фильтруемые столбцы (например, внешние ключи в
> связующих таблицах), **пагинацию** каталога (сейчас игр мало, но при росте
> нужна), **пул соединений** вместо открытия нового на каждый запрос, кэширование
> глобального топа. Схема к этому готова.

**Зачем смежные таблицы, почему не хранить жанры строкой?**
> Связь «многие-ко-многим»: у игры много жанров, у жанра много игр. Строкой это не
> выразить без дублирования и потери целостности. Смежная таблица `game_genres`
> хранит пары id с внешними ключами — это нормализованное и целостное решение.

**Что если два пользователя одновременно оценят одну игру?**
> Каждый пишет свою строку (`PRIMARY KEY (user_id, game_id)`), они не конфликтуют.
> Повторная оценка тем же пользователем — `ON CONFLICT DO UPDATE`, то есть upsert:
> обновляется существующая строка, дубля не возникает.

**Чем `gamedb_app` отличается от `postgres`?**
> `postgres` — суперпользователь (для DDL и миграций). `gamedb_app` — рабочая роль
> приложения: только SELECT/INSERT/UPDATE/DELETE на нужных таблицах, без права
> менять структуру. Если бы кто-то прорвался через инъекцию — он не смог бы
> уронить схему. Принцип наименьших привилегий.
