## Высокая

### H-1. `app.run(debug=True)` зашит в коде

- **Где:** `app.py:459` — `app.run(debug=True)`.
- **Проблема:** в debug-режиме Werkzeug включает интерактивный отладчик в
  браузере. Он защищён PIN-кодом, который вычисляется из стабильных
  локальных параметров (имя пользователя, MAC и т.п.) и в ряде сценариев
  поддаётся восстановлению. Если этот код будет запущен на внешнем хосте
  «как есть», это потенциальный RCE. Кроме того, в debug-режиме трейсбеки
  с исходниками и значениями переменных видны в браузере любому, кто
  открыл ошибку.
- **Исправление:** читать флаг из `.env`, по умолчанию — `False`.
  Например:
  ```python
  debug = os.getenv("FLASK_DEBUG", "false").lower() == "true"
  app.run(debug=debug)
  ```
  и добавить `FLASK_DEBUG=true` только в локальный `.env`.

### H-2. `SECRET_KEY` имеет слабое значение по умолчанию

- **Где:** `app.py:23` — `app.secret_key = os.getenv("SECRET_KEY", "dev-secret-change-me")`.
- **Проблема:** если `.env` не подгружен или переменная не задана,
  сервер запускается со строкой `"dev-secret-change-me"`. Сессии Flask
  подписываются этим ключом — атакующий, знающий строку, может подделать
  cookie `session` (включая `user_id` и `csrf_token`) и войти под любым
  аккаунтом. Иными словами, дефолт-значение даёт полный обход
  аутентификации и CSRF.
- **Исправление:** не использовать дефолт-значение. Лучше упасть при
  старте, чем работать с предсказуемым ключом:
  ```python
  app.secret_key = os.environ["SECRET_KEY"]
  ```
  При отсутствии переменной приложение не запустится — это именно то,
  что нужно. PROJECT_LOG уже говорит, что `SECRET_KEY` должен браться
  из `.env` — стоит привести код в соответствие с заявлением.

## Средняя

### M-1. Нет длины у новых имён `new_*_name(s)` — падение транзакции

- **Где:** `app.py:293, 295, 300, 305, 310` (POST `/admin/add_game` и
  `/admin/edit_game`); `validators.py:parse_new_names` и `db.py:_clean_names`.
- **Проблема:** для пользовательских имён жанров/тегов/платформ
  (`VARCHAR(100)`) и разработчиков/издателей (`VARCHAR(200)`) на сервере
  длина **не проверяется** перед `INSERT`. Если админ введёт строку
  длиннее лимита — PostgreSQL вернёт `StringDataRightTruncation`,
  внешний `except Exception` в маршруте откатит транзакцию и покажет
  обобщённое «Ошибка при сохранении игры», что неинформативно.
- **Исправление:** добавить `validate_new_name(name, max_len)` (например,
  один общий валидатор) и применять его в `parse_new_names` / отдельно
  к `new_developer_name`/`new_publisher_name`. Сообщения должны быть
  конкретными: «название тега не длиннее 100 символов».

### M-2. Описание игры `description` без верхней границы длины

- **Где:** `app.py:289, 390`; `schema.sql` — поле `TEXT`.
- **Проблема:** теоретически админ может отправить мегабайт текста.
  Это не уязвимость (маршрут под `@admin_required`), но даёт возможность
  раздуть таблицу `games`. Также `<p>{{ game.description }}</p>` в
  `game.html` не сохранит переносы строк (HTML их сворачивает), что
  ухудшит UX для больших текстов.
- **Исправление:** ввести явный лимит (например, 5000 символов) в
  `validate_game_description` и применять и в `add_game`, и в `edit_game`.

### M-3. Откат транзакции после ошибки внутри `store_links` (try/except)

- **Где:** `db.py:115-119`, внутри `get_game_by_id`.
- **Проблема:** последний шаг — `cur.execute(store_links_sql, …)` —
  обёрнут в `try/except: game["store_links"] = []`. Логика рассчитана
  на случай, когда таблицы `game_store_links` ещё нет (старая БД до
  миграции). Но `except Exception` ловит **любое** исключение, включая
  настоящие ошибки соединения. Тогда транзакция psycopg остаётся в
  состоянии «aborted», а на выходе из `with conn:` будет попытка
  COMMIT — psycopg 3 в этом случае вернёт `InFailedSqlTransaction` или
  тихо откатит, но в любом случае ошибка маскируется.
- **Исправление:** сузить except до конкретного исключения
  (`psycopg.errors.UndefinedTable`) либо вообще убрать try/except, раз
  таблица уже точно существует в схеме (PROJECT_LOG это подтверждает).

### M-4. `SESSION_COOKIE_SECURE` по умолчанию `false`

- **Где:** `app.py:28-30`.
- **Проблема:** если деплоить под HTTPS и забыть выставить
  `SESSION_COOKIE_SECURE=true` в `.env`, cookie с CSRF-токеном и
  `user_id` будет ходить и по HTTP. Это легко упустить.
- **Исправление:** оставить как есть, но завести запись в `.env.example`
  и в README/PROJECT_LOG: «в проде обязателен `SESSION_COOKIE_SECURE=true`».
  Альтернатива — наоборот, по умолчанию `True`, и явный `false` для dev.

### M-5. Админ-формы теряют введённые значения при ошибке валидации

- **Где:** `app.py:319-324, 346-351, 420-426, 449-455` — `render_template`
  в ветке ошибок не передаёт `title`, `release_date`, выбранные
  `genre_ids/tag_ids/platform_ids`, новые имена.
- **Проблема:** UX. Пользователю, заполнившему большую форму,
  при опечатке в дате выхода придётся набирать всё заново. В случае
  редактирования (`admin_edit_game`) ситуация хуже: при ошибке POST
  форма показывает **исходные** значения игры, а не то, что админ
  редактировал, — он теряет правки и может этого не заметить.
- **Исправление:** добавить в `render_template` параметр `form` со
  всеми введёнными значениями и подставлять его в `value=…` /
  `selected` / `checked` шаблона.

### M-6. Дубликаты `developers`/`publishers` по имени

- **Где:** `db.py:567-573, 575-582, 715-722, 725-732` — ветки
  `INSERT INTO developers/publishers (name) VALUES (%s) RETURNING …`
  без `ON CONFLICT`. В `schema.sql:11-19` у этих таблиц **нет UNIQUE**
  по `name`.
- **Проблема:** если админ вписал в «нового разработчика» имя, уже
  существующее в `developers`, создастся вторая запись. Со временем
  это разрастёт справочник дубликатами, а UI выпадающего списка
  будет показывать «CD Projekt Red», «CD Projekt Red», «CD Projekt Red».
- **Исправление:** либо
  - добавить `UNIQUE (name)` в `developers` и `publishers` и
    использовать тот же приём `ON CONFLICT (name) DO UPDATE SET
    name = EXCLUDED.name RETURNING id`, как для жанров/тегов; либо
  - перед `INSERT` делать `SELECT developer_id FROM developers WHERE
    name = %s` и использовать существующий id, если найден (find-or-create
    без UNIQUE).
  Первый вариант надёжнее (защита от гонок).

### M-7. В админских маршрутах валидируется только `title` и `release_date`

- **Где:** `app.py:313-315, 414-416`.
- **Проблема:** `developer_id`, `publisher_id`, `genre_ids`, `tag_ids`,
  `platform_ids` проходят только через `safe_int(min_val=1)` — это
  отфильтровывает мусор, но не проверяет, что id реально существуют.
  Сейчас это «спасает» внешний ключ в PostgreSQL: при попытке
  `INSERT INTO game_genres … REFERENCES genres` транзакция откатится,
  и пользователь увидит «Ошибка при сохранении игры». Это работает,
  но даёт обобщённое сообщение там, где могло бы быть конкретное.
- **Исправление:** опционально проверить существование id в `db.py`
  (например, `SELECT 1 FROM developers WHERE developer_id = %s`) и
  возвращать осмысленную ошибку. Не критично — FK уже защищает БД.

## Низкая

### L-1. LIKE-метасимволы `%` и `_` в `search_games` не экранируются

- **Где:** `db.py:128-147`, `cur.execute(sql, (f"%{query}%",))`.
- **Проблема:** пользователь, введя `%`, получит «всё»; `_` — все
  однобуквенные совпадения. Это не SQL-инъекция (параметр уходит как
  значение), но поиск ведёт себя странно для подобных запросов.
- **Исправление:** заменить `%` и `_` на `\%` и `\_` в строке запроса
  (плюс `ESCAPE '\'` в SQL) — либо оставить как есть, если это
  считается фичей.

### L-2. `try/except` в `get_game_by_id` слишком широкий

- См. M-3 — связанная находка. Здесь повторяю в контексте Низкой: с
  точки зрения багов в текущем рабочем состоянии БД, это безвредно,
  потому что таблица существует. Но любая будущая ошибка в этом
  запросе будет молча проглочена.

### L-3. `_clean_names` частично дублирует `parse_new_names`

- **Где:** `db.py:_clean_names`; `validators.py:parse_new_names`.
- **Проблема:** маршрут уже зовёт `parse_new_names` (case-insensitive
  дедупликация + strip), потом `create_game`/`update_game` вызывают
  `_clean_names` (case-sensitive дедупликация + strip). После
  `parse_new_names` второй проход почти всегда no-op. Не баг, но
  лишний код.
- **Исправление:** оставить одну функцию (логика дедупликации лучше
  case-insensitive). Удалить `_clean_names` из `db.py`.

### L-4. `safe_int` не отбраковывает дробные числа

- **Где:** `validators.py:safe_int`.
- **Проблема:** `int("3.5")` бросит `ValueError` — OK, вернётся None.
  Но `int(3.5)` (если пришла float) даст 3. В web-формах все значения
  приходят строками, так что на практике это безопасно. Уровень
  «мелочи».

### L-5. `validate_game_title` проверяет длину **до** strip

- **Где:** `validators.py:98-104`.
- **Проблема:** `if len(title) > GAME_TITLE_MAX_LEN` — берётся
  оригинальная длина. Если в строке пробелы по краям, лимит может
  «съесть» один символ. Однако маршрут уже делает `.strip()` до
  валидации (`app.py:287, 388`), так что в текущем коде проблема не
  проявляется.

### L-6. `load_dotenv()` вызывается дважды

- **Где:** `app.py:18` и `db.py:6`. Это не баг, но дублирование.
- **Исправление:** оставить только в `app.py`, тогда `db.py` будет
  читать уже подгруженный `os.environ`. Можно оставить и так — побочных
  эффектов нет.

### L-7. `get_user_by_id` вызывается на каждом запросе через `inject_user`

- **Где:** `app.py:60-64` и `app.py:88` (`admin_required` тоже его
  зовёт — на админских маршрутах вышло **два** запроса в БД к users
  на один request).
- **Проблема:** перфоманс, не баг.
- **Исправление:** кэшировать `current_user` в `g.user` за один проход.

### L-8. `game.html: {% if game.avg_score %}` и `{% if user_rating %}`

- **Где:** шаблон.
- **Проблема:** теоретически, оценка 0 — falsy. В нашей схеме это
  невозможно (`CHECK (score BETWEEN 1 AND 10)`), но проверка
  `is not none` была бы строже.

### L-9. Описание разработчика/издателя дублирующиеся: в `seed.sql` шесть студий и шесть издателей, при этом нет `UNIQUE`

- См. M-6. Текущий seed не содержит дублей, но повторный запуск
  скрипта (или seed_delta поверх seed) **создаст дубликаты**. У
  таблиц `developers`/`publishers` отсутствует UNIQUE по `name`, в
  отличие от `genres`/`tags`/`platforms`. Это асимметрия схемы,
  стоит как минимум зафиксировать в PROJECT_LOG.

### L-10. Гонки при `find-or-create` справочников при параллельных запросах

- **Где:** `db.py: create_game`, `update_game` — `INSERT … ON CONFLICT …`
  по `genres/tags/platforms`.
- **Проблема:** для жанров/тегов/платформ `ON CONFLICT (name)` защищает
  от гонки, спасибо UNIQUE. Для разработчиков/издателей — без
  UNIQUE и без `ON CONFLICT` — две параллельных POST-формы создадут
  две одинаковых строки. Учебный проект, маловероятно, но всё же.

## Чек-лист ручного тестирования

Прокликать перед защитой. Это **краевые случаи**, на которые код
реально опирается; их легко забыть проверить.

### Аутентификация / сессии
- [ ] Регистрация с занятым `username` → дружелюбная ошибка, никакого 500.
- [ ] Регистрация с занятым `email` → то же.
- [ ] Логин с правильным username и неверным паролем → «Неверный логин
      или пароль» (обобщённо).
- [ ] Логин с несуществующим username → ровно то же сообщение
      (не «пользователь не найден»).
- [ ] Логин → перезагрузить страницу → в навбаре виден username, в
      нижнем углу при F12 cookie `session` с `HttpOnly=true`, `SameSite=Lax`.
- [ ] Выход → cookie `session` ушёл, повторное открытие `/profile`
      редиректит на `/login`.

### CSRF
- [ ] curl/Postman: `POST /rate/1 score=8` **без** `csrf_token` → HTTP 400.
- [ ] То же с **неправильным** `csrf_token` → HTTP 400.
- [ ] То же с пустой сессией (без cookie) → HTTP 400.
- [ ] `POST /admin/add_game` без токена → HTTP 400.

### Оценки и границы score
- [ ] Оценить игру `score=1` → принято.
- [ ] `score=10` → принято.
- [ ] `score=0` → flash об ошибке валидации.
- [ ] `score=11` → flash об ошибке.
- [ ] `score=abc` → flash «должно быть целым».
- [ ] Поставить оценку, потом изменить её (другая цифра) → строка в
      `ratings` одна, `score` обновился, `created_at` подскочил (`now()`).

### Поиск
- [ ] Пустой запрос → форма пустая, список пуст, без ошибок.
- [ ] Запрос только из пробелов (`   `) → `.strip()` → пусто → ничего.
- [ ] Запрос длиннее 200 символов → flash об ошибке (если просочится
      через HTML-валидацию).
- [ ] Запрос с `%` или `_` → находит «всё»/однобуквенные совпадения
      (известное поведение, см. L-1).
- [ ] Запрос с SQL-метасимволами `'); DROP TABLE games; --` → возвращает
      пустой результат, БД жива.

### Фильтры каталога
- [ ] `/?genre_id=3` (RPG) — 4 игры.
- [ ] `/?genre_id=3&tag_id=4` (RPG + dark) — 2 игры.
- [ ] Жанр + редкий тег без пересечений → «По выбранным фильтрам
      ничего не найдено».
- [ ] `/?genre_id=abc` → `safe_int` вернёт None → каталог как обычно.
- [ ] `/?genre_id=-1` → то же.
- [ ] `/?genre_id=99999999` (несуществующий) → пустой результат (LEFT
      JOIN с ON-условием не найдёт совпадений) → «ничего не найдено».

### Рекомендации
- [ ] **Гость** (без логина) → блок «Популярное сейчас» с до 4 игр.
- [ ] **Новый аккаунт** (0 оценок) → блок «Популярное сейчас», игры
      из global top, без своих оценённых.
- [ ] Оценить 1, 2 игры → блок всё ещё «Популярное сейчас» (cold start
      порог 3).
- [ ] Оценить ровно 3 → блок переключился на «На основе ваших оценок».
- [ ] Оценить все 8 игр → блок пуст (нечего рекомендовать, candidates
      пуст, padding тоже).
- [ ] Оценить 3–4 игры с тегом `dark` на 9–10 → в блоке должны
      появиться другие dark-игры с высоким `rec_score`.
- [ ] Игра, которая уже оценена пользователем, в блоке рекомендаций
      **не должна** появляться.

### Похожие игры
- [ ] Открыть Witcher 3 → внизу до 4 похожих, отсортированы по числу
      общих тегов.
- [ ] Открыть Portal 2 (теги co-op, sci-fi) → если других co-op нет —
      должны появиться игры по sci-fi или «Нет похожих игр».

### Карточка игры
- [ ] `/game/9999` (несуществующий) → 404.
- [ ] `/game/abc` → 404 (Flask конвертёр `<int:>` отбракует).
- [ ] У игры без описания/даты/dev/pub поля не отрисовываются
      (условные `{% if %}`).

### Админ-маршруты (`/admin/add_game`, `/admin/edit_game/<id>`)
- [ ] Гость → `/admin/add_game` → редирект на `/login` + flash.
- [ ] Не-админ → `/admin/add_game` → HTTP 403.
- [ ] Не-админ → POST на `/admin/add_game` (curl) → HTTP 403 (декоратор
      работает на оба метода).
- [ ] Админ → форма с **пустым** title → flash «не может быть пустым».
- [ ] Админ → дата `2026-02-30` → flash «неверный формат».
- [ ] Админ → дата `2027-12-31` (будущее) → принято (ограничения нет).
- [ ] Админ → выбран существующий разработчик **и** вписан новый →
      создаётся новый, выбор игнорируется (приоритет `new_*_name`).
- [ ] Админ → новый тег с тем же именем, что и существующий (в любом
      регистре) → дубликат не создаётся (`ON CONFLICT (name)`).
- [ ] Админ → новый разработчик с уже существующим именем → **создастся
      второй** (см. M-6).
- [ ] Админ → отметить чекбокс **и** вписать тот же тег в «новые» →
      один тег, один INSERT в `game_tags` (дедупликация через `set`).
- [ ] Админ → имя нового тега длиной > 100 символов → транзакция
      откатится, flash «Ошибка при сохранении» (см. M-1).

### Редактирование игры
- [ ] Открыть `/admin/edit_game/9999` → flash «Игра не найдена» +
      редирект.
- [ ] Открыть форму → поля предзаполнены, чекбоксы текущих
      жанров/тегов/платформ отмечены, dev/pub выбран в `<select>`.
- [ ] Сменить title → сохранить → редирект на `/game/<id>`, новый
      title виден на карточке.
- [ ] Снять все жанры → сохранить → на карточке нет блока «Жанры».
- [ ] Добавить новый тег через «новые» → виден на карточке и в
      выпадающем списке фильтра.
- [ ] Сменить разработчика на нового → старая запись `developers`
      остаётся (orphaned), это намеренно.
- [ ] Внести правки, отправить **с пустым title** → flash об ошибке,
      форма показывает **исходные** значения, правки потеряны
      (см. M-5).

### Профиль
- [ ] Гость → `/profile` → редирект на `/login` + flash.
- [ ] Новый аккаунт без оценок → статистика не показывается, текст
      «вы ещё не оценили».
- [ ] После 3 оценок → статистика обновилась (`games_rated`,
      `avg_score_given`).

### Менее очевидное
- [ ] Войти, остаться на странице, **с другого устройства** убрать
      `is_admin` (`UPDATE users SET is_admin=false WHERE …`),
      обновить страницу → кнопка «Добавить игру» исчезла, доступ к
      `/admin/add_game` → 403 (флаг читается заново на каждом запросе).
- [ ] Открыть две вкладки `/admin/edit_game/1`, в первой сохранить
      изменения, во второй — тоже сохранить со старыми значениями →
      изменения первой будут перезаписаны (нет блокировки версии,
      это ожидаемо для простой админки).
- [ ] В curl послать `POST /rate/1 score=8` с правильным CSRF, но
      **без** cookie с `user_id` → flash «войдите» + редирект на login,
      БД не изменилась.

## Финальная оценка

Серьёзных дыр нет — параметризация, CSRF, контроль доступа и
хэширование паролей реализованы корректно. Главное к чинке —
`debug=True` и дефолт `SECRET_KEY` (H-1, H-2): обе строчки правки на
5 минут, но они снимают «продакшен-катастрофу». Остальное — это
качество кода и UX (длина новых имён, перенос значений в форму при
ошибке, дубликаты разработчиков), важное для защиты, но не для
безопасности.
